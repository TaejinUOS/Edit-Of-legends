# 분석 속도 측정

## 2026-09-23: 예시녹화본.mp4

Windows 개발 PC에서 1920×1080, 60fps 영상의 처음 300초를 측정했다. FFmpeg 디코더는 4스레드, 샘플 간격은 0.5초, 추출 영역은 K/D/A와 F 점멸 HUD 두 곳이다. 각 항목을 순서대로 한 번씩 실행했으며, 아래 시간은 성능 보장값이 아니다.

| 단계 | 시간 |
| --- | ---: |
| 영상 스트림 읽기 및 복사 | 0.2초 |
| 전체 프레임 디코딩 | 15.5초 |
| 디코딩 후 0.5초 간격 선택 | 15.7초 |
| 기존 회색조·HUD 추출 필터 | 37.6초 |
| rawvideo 출력 | 37.6초 |
| Node 파이프로 읽기 | 37.6초 |
| `sampleFrames()`에서 프레임 분리 | 37.6초 |

전체 화면에 `format=gray`만 적용해도 37.6초였다. 따라서 추가 시간은 주로 전체 화면의 회색조 변환에서 발생하고, HUD 결합·파이프 전달·Node 프레임 분리는 이 측정에서 큰 추가 비용을 만들지 않았다.

HUD를 먼저 자르고 밝기 성분을 추출한 뒤, 작은 영역에만 `lut=y='(val-16)*255/219+0.5'`를 적용한 후보는 15.6초였다. 기존 출력과 후보 출력은 모두 1,713,600바이트이며 SHA-256 해시가 `dc7fe98919606f512c169e57c194c7c17aee49f475a6802e624a27131f37eb99`로 같았다. 이 영상의 5분 구간에서 픽셀 단위로 동일한 결과를 약 2.4배 빠르게 만들었다.

## 엔진 적용 및 전체 영상 검증

`engine/media.js`의 복수 HUD 추출에 최적화를 적용했다. ffprobe가 픽셀 형식을 `yuv420p`, 색상 범위를 `tv`로 확인한 영상에만 사용한다. 다른 픽셀 형식·색상 범위, 메타데이터가 없는 이전 소스와 단일 HUD 추출은 기존 변환을 사용한다. 홀수 좌표와 크기를 보존하기 위해 `crop`에 `exact=1`을 지정했다.

약 26분 50초의 전체 예시 영상을 완료 캐시 없이 재분석한 결과:

| 항목 | 기존 기록 | 적용 후 |
| --- | ---: | ---: |
| 전체 분석 시간 | 224.389초 | 107.758초 |
| 자동 선택 디코더 스레드 | 4 | 5 |
| OCR 샘플 수 | 3,220 | 3,220 |
| 이벤트 수 | 23 | 23 |
| 최종 K/D/A | 6/7/7 | 6/7/7 |
| K/D/A 판독률 | 96.9565% | 96.9565% |

전체 샘플(신뢰도·점멸 상태 포함), 이벤트, 최종 K/D/A, 경고, 게임 시계 샘플과 오프닝 구간을 구조적으로 비교해 모두 일치했다. 소요 시간은 약 52% 감소했다. 전체 실행 비교는 자동 스레드 수가 다르고 기존 기록과 비교한 단일 실행 관측값이며, 동일한 4스레드 조건의 5분 비교는 위 표를 참고한다. 원본 검증 데이터는 로컬 `.eol/luma-validation.json`에 저장했다.

1080p·1440p 합성 영상의 0~255 밝기 값, 홀수 HUD 경계, 전체 범위 색상 영상의 기존 경로도 픽셀과 타임스탬프가 일치했다. `npm test`는 50개 통과, 예전 녹화 파일이 필요한 4개 건너뜀, 실패 0개였다. `npm run check`도 통과했다. 출력 호환성이 유지되므로 분석 캐시 리비전은 유지한다.

재측정 명령:

```powershell
npm run profile:decode -- "src-video/예시녹화본.mp4" 300
npm run profile:filter -- "src-video/예시녹화본.mp4" 300
```

## 디코더 스레드 설정 재사용

선택한 스레드 수를 데이터 폴더의 `decoder-profiles/`에 원자적으로 저장한다. 서버는 해당 인스턴스의 상태 폴더를 사용하고 CLI는 `EOL_DATA_DIR` 또는 프로젝트 `.eol`을 사용한다. CPU 모델·코어 수·사용 가능한 병렬도, OS·Node 버전, FFmpeg 경로·크기·수정 시각, 해상도·FPS·픽셀 형식·색상 범위, OCR 워커 수·샘플 간격·HUD 영역이 키에 포함된다. 영상 파일명과 분석 범위는 포함하지 않으므로 조건이 같은 다른 영상에도 재사용한다.

30일이 지나거나 조건이 달라지면 재측정한다. 저장값이 현재 허용 후보에 없거나 저장 파일이 손상된 경우도 다시 측정하며, 읽기·저장 실패는 분석을 중단시키지 않는다. 디코딩·OCR·튜닝 구현 변경으로 성능 특성이 달라지면 `engine/decoder-cache.js`의 `PROFILE_REVISION`을 올린다. 분석 결과 캐시와는 별개다.

예시 영상의 170~210초 구간을 완료 분석 캐시 없이 별도 Node 프로세스에서 연속 실행했다:

| 항목 | 최초 실행 | 프로세스 재시작 후 |
| --- | ---: | ---: |
| 소요 시간 | 17.062초 | 6.137초 |
| 스레드 비교 횟수 | 10 | 0 |
| 선택 스레드 | 5 | 5 |
| `decoderThreadsCached` | false | true |

약 10.9초를 절약했고 OCR 샘플 80개, 이벤트 2개, 게임 시계·오프닝 구간·최종 K/D/A·경고가 모두 일치했다. 전체 영상 시간은 이번 변경 후 다시 측정하지 않았다. 검증 원본은 로컬 `.eol/decoder-validation-cold.json` 및 `.eol/decoder-validation-warm.json`에 있다. 캐시 조건 변경, 디스크 재로딩, 만료·손상·저장 실패 테스트를 포함해 `npm test`는 52개 통과, 이전 녹화 파일이 필요한 4개 건너뜀, 실패 0개였고 `npm run check`도 통과했다.

## 게임 시계와 본 분석 디코딩 통합

`engine/clock-sampling.js`에서 기존 2초 간격의 시계 관측 시각이 본 분석의 샘플 시각과 일치하는 경우 시계 HUD를 함께 추출한다. 안정된 시계가 확보되면 시계 OCR을 중단한다. 선택 구간 앞의 시계 관측과 짧은 클립 끝 이후의 추가 관측은 유지하며, 분석 결과에는 선택 구간 안의 K/D/A·점멸 샘플만 포함한다. 두 관측 시각이 맞지 않는 임의 간격이나 소수점 시작 시각은 기존 별도 추출을 사용한다.

전체 예시 영상을 완료 분석 캐시 없이 같은 5스레드 설정을 재사용해 순차 비교했다:

| 항목 | 시계 별도 추출 | 통합 추출 |
| --- | ---: | ---: |
| 전체 분석 시간 | 97.174초 | 89.986초 |
| K/D/A·점멸 샘플 | 3,220 | 3,220 |
| 시계 샘플 | 31 | 31 |
| 이벤트 | 23 | 23 |

약 7.2초(7.4%) 단축됐고 모든 OCR 샘플, 시계 샘플, 이벤트, 오프닝 구간, 최종 K/D/A와 경고가 구조적으로 일치했다. 170~210초만 선택한 실제 영상도 기존 결과와 일치했다. 기록은 `.eol/clock-validation-before.json`과 `.eol/clock-validation-after.json`에 있다. 같은 환경의 단일 실행 비교이며 다른 영상의 개선 폭을 보장하지 않는다.

짧은 선택 구간의 앞뒤 관측, 소수점 시작과 비정규 간격, 시계 판독 실패의 탐색 한도, 취소를 테스트했다. 1080p·1440p에서 세 번째 시계 영역의 픽셀이 기존 단독 추출과 일치하는 것도 확인했다. `npm test`는 57개 통과, 이전 영상 파일이 필요한 4개 건너뜀, 실패 0개였고 `npm run check`도 통과했다.
